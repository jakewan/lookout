# lookout

A single vantage point over everything you have in flight. lookout gathers recent activity from git, GitHub, AI coding sessions, and files supplied by other tools, groups it into workstreams you define, and reports how recently each one moved and whether every input it relies on is healthy.

lookout is at an early stage, and has no releases yet. To build it from a clone, run `just install`, which installs it to `~/.local/bin` using the toolchain `mise.toml` pins. Reading git repositories needs git 2.36 or later, and reading GitHub needs the [GitHub CLI](https://cli.github.com/), logged in to github.com (`gh auth login`) or with `GH_TOKEN` set. Reading Claude Code sessions needs the configuration directories that hold them, listed as `config_dirs`, and git, which places each session in the repository at its working directory when lookout reads. [docs/vision.md](docs/vision.md) describes the dashboard it is the data layer for.

Run `lookout show` to read a setting's workstreams in a terminal. It lists them in their stated order, one row each, in plain text wrapped at 80 columns. Each row shows:
- the workstream's title, or its id where it has none, with the whole id in brackets at the row's end wherever the label is not the id, since commands take the id;
- how long since the workstream was last touched;
- `stale` when nothing it holds was touched within `event_window`, or `unread` when nothing was read for it on this read, neither a member nor a joined item;
- its members per input, with how many no input supplied, and, counted apart, the items a key, a pull request or a parent joined to it (`github 1 +2 joined`).

A row starting with `!` draws on an input that is degraded or in error, so its figures may understate. Below the rows, a warning names each such input with its reasons, and each workstream that draws on one. The last line counts the unplaced and dismissed items and the completed workstreams, and it starts with `!` whenever any input is degraded or in error, since such an input can leave those counts short. Tabs and line breaks in a name are shown as spaces. A name holding any other control character, an invisible formatting character, or a space other than the plain one is shown quoted, with that character escaped. A name or title longer than 24 characters is cut and ends in `~`, but the bracketed id never is: it goes on a line of its own where it does not fit, and one too long for any line passes 80. The width counts every character as one column, so wide characters, such as many in Chinese, Japanese or Korean, can push a line past 80. The view is drawn from the same readout `lookout read --json` writes.

Run `lookout view` to see the same readout in a browser. It writes one page to `$XDG_CACHE_HOME/lookout/<setting>/view.html` (`~/.cache/lookout/<setting>/view.html` by default), and beside it `view.json`, the readout the page was drawn from, both readable only by you, and prints the page's path, so `xdg-open "$(lookout view)"` opens it. It selects a setting as every command does, by `--setting` or `LOOKOUT_CONFIG`. At the top, an overview lists the workstreams in their stated order, each by its title, with its id beside it, or by its id where it has none, and each as a lane marking its items' latest touches across `event_window`, with how long since it was last touched, `stale` or `unread` as `lookout show` marks them, and `behind its rank` when a workstream ranked below it was touched more recently. Beneath it, a mind map draws the setting at the center and its workstreams branching to both sides, down the right in stated order and back up the left, each branch running outward through its items, each labelled by its title with its id beside it, or by its id where it has none: a joined item hangs under the member it joined through, or one its parent joined under that parent, a branch under the pull request it was made from, and a member under its parent, wherever the workstream draws what it hangs from; a parent loop is cut at its first item, and the edge it gave up is drawn as a dashed link. An item several workstreams hold appears once, under the first that holds it as a member, or the first that holds it at all, with a dashed link to each other holder, and an edge the tree cannot show, such as a parent held by another workstream, is linked the same way. Branches are neutral until a cue colors one, loudest first: a workstream on a failing input is drawn in red, one behind its rank in amber, one with nothing read dashed, and a stale one faded, so on a setting where most are stale the rest still stand out. Select a node to see its handle, the id or `<input>:<id>` commands take, copy it, make the node the hub, or collapse what it holds. A switch shows the same items as lists instead, grouped by input, each join saying what it joined through; with script turned off the page shows the lists in place of the map. Below the map or the lists, the unplaced items, those `lookout unplaced` lists, are shown under a count, most recently touched first, each by the `<input>:<id>` token `lookout adopt` and `lookout dismiss` take, quoted as `lookout unplaced` quotes one, with its title, its state and how long since it was touched; pass a quoted token, or one holding a space, to the shell in single quotes. An input that is degraded or in error is named above the overview with its reasons, and a workstream drawing on one is marked `!`; an input the setting expects to be absent is not shown. **The page never leaves your machine: it holds everything it shows in the one file, runs no script but lookout's own, which its content security policy pins by hash and which neither navigates nor opens a connection, and blocks every fetch it could make on its own, so opening it reaches nothing; only an item's link, when you click it, goes to the network, and it opens in a new tab so the page stays as it was.** It is a snapshot of one read, so run `lookout view` again, then reload, to refresh it. While it stays open, the page says how long ago its read was, from the browser's clock, and marks the read old once it passes two hours, or the duration `--read-old-after` gives, such as `--read-old-after 30m`; Go writes that schedule into the page ahead of time, so the script only shows the step for the moment, and with script off the page shows only its as-of time. The page names its read exactly, as the `generated_at` in `view.json`, in the tooltip hovering its as-of time shows, and to the millisecond in that time's `datetime`, so you and an agent reading that file can tell you are looking at the same read. Running it again replaces both files, as does running it for another configuration file with the same setting name. `lookout view --readout <file>` draws a readout `lookout read --json` saved earlier, or one from stdin with `-`, without reading any configuration; it must meet readout.v1, and its `setting` names the directory whose page and `view.json` it replaces.

`lookout read --json` writes the readout itself, in the [`readout.v1`](schema/readout.v1.json) contract, for any renderer. Each workstream carries two verdicts lookout decides once, so every view, and an agent reading the readout, draws the same: `active` when it holds an item touched within `event_window`, and `behind` when a workstream listed after it was touched more recently. `show` and `view` mark `stale` a workstream read but not `active`, and the page's count of active workstreams is the count `snapshot` records. Besides each workstream's items, its `workstream_links` relate live workstreams through what they hold: `shared_item` where both hold the same item, as a member or a join, and `parent` where one holds an item's parent and the other the item, each link listing the items behind it as `<input>:<id>`.

Run `lookout snapshot` once a day to keep a baseline of how often new work appears and how stale your workstreams are. Read beside the gesture log in the same directory, it shows how each new item was placed, and each record lists the items a key, a pull request or a parent joined apart from those a command or a hand edit placed. Each record's `backlog` lists the items it takes as already there rather than arriving, none of which ever counts as an arrival: on a setting's first record, everything unplaced or joined; on a later one, what an input that was failing until then, or is newly configured, shows, and each item joined for the first time that last moved before `discovery_window`. So an item can be listed under `backlog` as well as under `joined` or `unplaced`. With a `github` input configured, each record also lists the pull requests you authored within your github.com `forge_owners` that merged since the last record that read them. To count them, skip records whose `merged_prs.failed` is set, since a failed read lists nothing, and group by each entry's `merged_at`: a merge GitHub's search finds late is listed on a later record. The first snapshot of a date is kept, so running it again later that day changes nothing.

## Configuration

Each setting, such as `personal` or `work`, has one configuration file, `$XDG_CONFIG_HOME/lookout/<setting>.yml` (`~/.config/lookout/<setting>.yml` by default). A setting name uses lowercase letters, digits, `-` and `_`. lookout reads exactly one file per invocation: the one `--setting <name>` names, or else the path in `LOOKOUT_CONFIG`, or else the only file in that directory, unless that file sets `explicit_only`. With several files there and neither given, it refuses rather than combining settings, whichever of them set `explicit_only`.

```yaml
event_window: 168h
discovery_window: 72h
forge_owners: [your-name, gitlab.com/your-name]
key_pattern: '([A-Z][A-Z0-9]+-[0-9]+)'
inputs:
  - name: code
    kind: git
    repos: [~/code/*]
    ignore_branches: [worktree-*, dependabot/*/*]
  - name: hub
    kind: github
  - name: sessions
    kind: claude_code
    config_dirs: [~/.claude]
  - name: tracker
    kind: supplied
    supplied: tracker.json
    max_age: 24h
workstreams:
  - name: search
    title: Search revamp
    members:
      - hub:your-name/app#12
      - code:your-name/app:feature/search
  - name: billing
    members:
      - tracker:ABC-123
    completed: 2030-06-15
```

- **`explicit_only`**: `true` keeps this setting from being read as the only file in the directory, so every command, reads included, uses it only when `--setting` or `LOOKOUT_CONFIG` names it. Without that, a command typed for another setting would edit or record into this one. A command that names neither is refused, and the refusal writes nothing. `LOOKOUT_CONFIG` counts as naming the setting even when a shell profile exports it, so exporting it for good gives up the protection. A scheduled command that relied on the lone file, such as `lookout snapshot`, needs `--setting` or `LOOKOUT_CONFIG` once this is set. A value lookout cannot read as a boolean is refused, and so is a file with a line that looks like it sets the key, such as `explicit-only:`, `ExplicitOnly:` or an indented `explicit_only:`, where lookout finds no top-level `explicit_only` it can read: a misspelling or a broken file never leaves the setting open to being chosen by default. A file lookout cannot read at all is still chosen, so that its error is reported.
- **`event_window`**: how far back a workstream's events reach, and the window within which it counts as active. A Go duration such as `24h` or `90m`, with no unit for days, in whole seconds. The default is two weeks.
- **`discovery_window`**: how recently an item a git, GitHub or Claude Code input finds, or a `supplied` input marked `windowed`, must have moved to be offered as unplaced. It defaults to `event_window`. A workstream's members, the git branches, pull requests and supplied items a key joins to it, and the supplied items a parent joins to it, are read at any age.
- **`forge_owners`**: the owners whose repositories, pull requests, issues and sessions this setting admits. Nothing else is read into it. A bare name is an account or organization on github.com, and an owner on another host is written `host/owner`. It is required once a `git`, `github` or `claude_code` input is configured, and a `github` input needs at least one github.com owner.
- **`key_pattern`**: a regular expression in Go's syntax, written in single quotes, with one capture group around a ticket key, such as `'([A-Z][A-Z0-9]+-[0-9]+)'`. On every read, an item whose key is the id of a supplied member joins that member's workstream, without being added to this file, and the readout and `lookout show` mark it as joined. The key is what the group captures in the first match: in a pull request's title, or else its branch; in a git branch's name; and in a Claude Code session's branch. A pull request's description is read for every key it names, and the pull request joins the workstream of each, so one whose description says `Part of ABC-12, follow-up to ABC-11` joins ABC-12's workstream, and ABC-11's only if a workstream adopted it: as with titles, only a key that is an adopted member's id places anything. A supplied item's `notes` are read the same way, for every key, so an item a work container's notes tie to ABC-12 joins ABC-12's workstream however little else its supplier recorded; a supplier that fills `notes` with ticket descriptions joins each ticket to the workstream of every adopted ticket its description names. One item can so join several workstreams, and counts as a touch in each, so a release pull request listing several adopted tickets moves all of their workstreams; `lookout dismiss` keeps it out of them, though its branch, no longer following it, is then offered as unplaced. The pattern decides which spellings are keys: the example finds only upper-case ones, so to place lower-case branches such as `feature/abc-12`, write `'([A-Za-z][A-Za-z0-9]+-[0-9]+)'` or start the pattern with `(?i)`, at the cost of more stray tokens, such as `node-18`, being taken for a text's key. A key found compares with member ids without regard to case, so `abc-12` places work with member `ABC-12`. In a title or branch only the first key counts, so under the example pattern a title such as `Fix UTF-8 in ABC-12` carries `UTF-8`; narrow the pattern to your tracker's prefixes where that happens. A key belongs to the first live workstream, in their stated order, that names a supplied member with that id. It never takes an item a live workstream names, or one a completed workstream still holds because it has not moved since. lookout also searches github.com pull request titles and descriptions for each key that holds no quote, colon, parenthesis, backslash or space, so merged pull requests and colleagues' join too, but only those whose author the repository lists as an owner, member or collaborator, so your own pull request to an organization you contribute to without belonging joins only while `github` discovers it as your open one. A pull request that carries its key only in its branch joins only when it is your own open one within `discovery_window`. With a pattern set, the branch an open or draft pull request was made from, and a Claude Code session on that branch, follow the pull request into each live workstream holding it, whether it joined or you adopted it, so a branch need not name its ticket. The branch is matched by its repository and name, so your clone's `origin` must be the repository the branch was pushed to: a branch pushed to a remote other than `origin`, or a clone whose `origin` still names a repository since renamed, doesn't match, and a session on a detached checkout has no branch to match. A branch or session only its pull request places is read only within `discovery_window`. Claude Code sessions join only within `discovery_window`. A workstream that a key belongs to, or that holds an open pull request, draws on every `git`, `github` and `claude_code` input, and one a key belongs to on every `supplied` input too, whose notes may join it, so one that fails marks it with `!`, since that input may have kept a join from it. `lookout dismiss` keeps a joined item out until it moves again, and `lookout remove` of an item whose key is a member's id, or whose parent or ancestor is a member, leaves it joined. A pattern with no capture group or several, or one that matches an empty text, is refused.
- **`inputs`**: each input has a `name`, which uses the same characters as a setting name, and a `kind`:
  - **`git`**: the local branches of the repositories `repos` lists. An entry is a path or a glob pattern, `~/` is your home directory, and a relative entry is read from the configuration's directory. A pattern admits only directories that are repositories, and `**` is refused, so list each depth, such as `~/code/*` and `~/code/*/*`. The default branch is never offered. A pattern that finds no repository is reported as `missing`, unless `repos_may_be_empty: true` says it may: then finding none is healthy, so long as the directory the pattern searches from, the part before its first wildcard, exists and lookout can look into it. A mistyped directory is still reported, and so is one on a volume that is not mounted, but a mount point itself usually stays on disk, empty, while its volume is away, so start the pattern at least one directory inside the volume. The key covers every pattern in the input, so put a pattern that may be empty, such as a directory a tool fills with worktrees, in an input of its own. It can't be set with `expect_records: true`.
  - **`github`**: open pull requests you authored and open issues assigned to you, within the github.com owners, plus every member at any age and state, and with `key_pattern`, the pull requests a search of titles and descriptions for each key finds. An issue that is a sub-issue carries its parent issue's id as `parent` when the parent's owner is in `forge_owners` and the token can read it; a parent outside them is left out and never named, and one the token cannot read is left out without marking the input. It takes no settings of its own.
  - **`claude_code`**: Claude Code sessions in the configuration directories `config_dirs` lists, as one item per repository and branch. As in `repos`, `~/` is your home directory and a relative path is read from the configuration's directory.
  - **`supplied`**: a file an outside tool writes in the [`supplied.v1`](schema/supplied.v1.json) contract. `supplied` is its path, read from the configuration's directory when relative. `max_age` is how old its data may get before the input counts as stale. A supplied input offers every item it holds as unplaced, however old, unless `windowed: true` says to offer only those that moved within `discovery_window`, as the inputs lookout reads itself do; set it for a supplier that keeps a long history, such as every session ever run. An item a live workstream names, or one its `notes` or `parent` join, is kept at any age, and an item too old to be offered is not counted as dismissed either. An item may carry `notes`, free text such as the ticket section of the work container it ran in, which lookout searches for `key_pattern`'s keys, so a supplier never needs to know the pattern. Notes are never written to a readout, `lookout show`, `lookout view`, `lookout unplaced` or a snapshot. One longer than 4096 Unicode code points fails the contract and withholds the whole file, so a supplier with more text cuts it at whitespace, or leaves the field out, rather than cutting a key in two. An item may name its `parent`, the exact id of the item it sits beneath in the same file, such as a story's epic; lookout takes one parent per item, as mainstream trackers do, so any other relation belongs in its `links`, and places the item under a workstream that adopts its parent or an ancestor, as described under `workstreams`. A lookout built before `parent` was added refuses a file that uses it. A supplier reports its own faults in `supplier_status`, as `degraded` or `error`, and in `missing_fields`, any entry of which makes the input at least degraded: a field its source should have filled but did not belongs in `missing_fields`, whether on some items or all. A field an item has no value for by its nature, such as a due date on work that has none, is left off that item and reported nowhere, even when no item carries it, so the input stays `ok`.
  - **`ignore_branches`** (on `git` and `claude_code`): branch patterns never offered, matched as Go's `path.Match` does, so `*` stops at `/`.
  - **`awaiting`**: a file an outside tool writes in the [`awaiting.v1`](schema/awaiting.v1.json) contract, listing replies you owe: a review requested of you, a comment mentioning you, changes asked on your own work. It takes `supplied` and `max_age` as a `supplied` input does, and its health is judged the same way, except that an empty file is a quiet day. The supplier reports when you were last asked in each thread and when you last answered; the readout lists, under `awaiting`, the entries still waiting, and names under `awaiting_inputs` every awaiting input, so a setting with nothing waiting reads apart from one with no source. A reply owed is not an item: it never joins a workstream, a workstream cannot list it as a member, and `lookout adopt` and `lookout dismiss` refuse it. An entry may name its `subject`, an item of another input as `<input>:<id>`, and the readout then says which workstreams hold that item, or that it is unplaced, rather than show it twice. A failing awaiting input says so in its own health line and marks no workstream, count or snapshot, since none of them is read from it. `lookout show` and the page do not draw the entries yet.
  - **`expect_records`** (any kind but `awaiting`): an input that reads no items is degraded rather than healthy. Naming a supplied input's item in a workstream implies it.
- **`workstreams`**: in the order the readout lists them. `members` are `<input>:<id>` tokens:
  - `git` and `claude_code`: `owner/repo:branch`, or `host/owner/repo:branch` off github.com. A detached session is `owner/repo`.
  - `github`: `owner/repo#N`.
  - `supplied`: the id the supplier writes.

  `lookout unplaced` prints these tokens ready to paste. A workstream's `name` is its id, which commands take and lookout's history follows. `title`, which is optional, is what `lookout show`, `lookout view` and the readout label it with; it must be text, cannot be blank or hold a line break, and cannot be another workstream's id. `lookout rename <workstream> <title>` sets it and leaves the id alone, `lookout rename --clear <workstream>` removes it, and `lookout rename --id <workstream> <new-id>` changes the id instead. `lookout adopt --new` and `lookout move --new` take `--title` to title the workstream they create. `completed: YYYY-MM-DD` marks a workstream finished. It leaves the readout, and a member touched after that date is offered again. `lookout delete <workstream>` takes a workstream out of the file instead, so it is no longer counted among the completed ones, and only one that names no members, live or completed: take its members out with `lookout remove` or `lookout move` first, or keep its history by completing it, or by leaving it as it is once complete. A comment above its first line stays, and then reads as the next workstream's.

  A member pulls in what sits beneath it. On every read, an item whose `parent` is a live workstream's member joins that workstream, without being added to this file, and so does an item further down, such as a sub-task under a story under an adopted epic, through each parent its input reads, so adopting an epic places the tickets under it as they arrive, with no `adopt` for each. The nearest adopted ancestor decides: a sub-task under a story you adopted into one workstream joins that one, not its epic's, and where a hand edit names one ancestor in several live workstreams, the first in stated order takes it. The adopted ancestor itself need not be in the input, so a tracker export that leaves out its epics still places each story under its adopted epic, but every item between the two must be: a sub-task climbs only through a story the input supplies, so a supplier that writes only the current sprint's tickets should also write the parents of the tickets it writes, or a sub-task whose story it left out stays unplaced. This needs no `key_pattern`. The readout marks such an item `joined.by: parent`, unless another join placed it in the same workstream first, `lookout show` counts it with the other joins, and the page hangs it under its parent where the workstream holds it. As with every join, it never takes an item a live workstream names, `lookout dismiss` keeps it out until it moves again, and a windowed supplier's item it joins is kept at any age. A dismissal or a membership keeps out only the item it names, never what sits beneath it, so dismissing a story leaves its sub-tasks joined to the epic's workstream, and `lookout remove` of an item under an adopted ancestor leaves it joined to that ancestor's workstream. On GitHub it reaches only the issues the input reads, open ones assigned to you that moved within `discovery_window`, and climbs only through ancestors it reads, so a sub-issue whose parent nobody adopted and no read finds does not reach the epic above it.

`lookout adopt`, `move`, `remove`, `rename`, `order`, `complete` and `delete` edit this file in place and keep its comments and layout. They refuse a file whose YAML they cannot edit safely, such as one using anchors, tags, several documents or non-empty flow-style (`[...]`) workstream or member lists, and say what to change. Everything lookout records itself, the gesture log and the baseline, is under `$XDG_STATE_HOME/lookout/<setting>/` (`~/.local/state/lookout/<setting>/` by default), and is never hand-edited. That directory belongs to the configuration file that claimed it by writing to it first, so another file for the same setting, such as a copy in another checkout, is refused. The refusal says how to run against the file it belongs to; to try a copy without touching that history, run it with `XDG_STATE_HOME` set to another directory. Delete the directory's owner record, as the refusal names it, only when the file has moved for good.
