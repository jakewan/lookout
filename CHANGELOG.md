## [Unreleased]

### Added

- `lookout read --json` writes a readout of one setting's workstreams, unplaced items, and input health, read from files outside suppliers write, local git repositories, GitHub, and Claude Code sessions. Select the setting with `--setting` or `LOOKOUT_CONFIG`; a lone configuration file is used without either unless it sets `explicit_only`, and with several configured and none selected, lookout refuses. Each workstream carries its member items as their inputs reported them, and lists the members no input supplied. Completed workstreams are left out and counted in `completed_count`; an item the user dismissed is left out of `unplaced` and counted in `dismissed_count` until it is touched again, and a completed workstream's item is left out of `unplaced` until it is touched after the day the workstream was completed. (#5, #6, #7, #8, #9, #16)
- A configuration file per setting, at `$XDG_CONFIG_HOME/lookout/<setting>.yml`, listing the expected inputs (`name`, `kind`, and for a `supplied` input its `supplied` path and `max_age`, with an optional `expect_records`), the workstreams in their stated order with their `<input>:<id>` members and an optional `completed` date, and an optional `event_window`. A setting's name, taken from the file name, must use lowercase letters, digits, `-` and `_` however the file is selected. (#5, #6, #7)
- `explicit_only: true` keeps a setting from being chosen as the lone configuration file: every command, reads included, uses it only when `--setting` or `LOOKOUT_CONFIG` names it, and otherwise refuses without writing anything to the configuration or the setting's state. A value lookout cannot read as a boolean is refused, and a file is not chosen by default either when it has a line that looks like it sets the key, misspelled, indented or quoted, but no top-level `explicit_only` lookout can read. A file lookout cannot read at all is still chosen, so that its error is reported. (#16)
- Input health computed from each supplied file: missing, unreadable, written for another input, or reporting its own error is `error`; stale, last attempt failed, stamped ahead of the clock, failing its schema, repeating an item id, reporting itself degraded, naming missing fields, or empty where records are expected is `degraded`. An input is expected to have records when `expect_records` says so or a workstream names one of its items. A supplier's report can lower health but never raise it. (#5)
- `lookout adopt <input>:<id> <workstream> [--new]` adds an item to a live workstream, moving it out of any completed workstream that still lists it, `lookout order <workstream>...` moves workstreams to the front of the stated order, and `lookout complete <workstream>` marks one finished as of today. Each edits the configuration file in place, leaving every line it does not change exactly as written, and refuses rather than reformat a file it cannot edit that way or overwrite one that changed while it worked. (#6)
- `lookout move <input>:<id> <workstream> [--new]` moves an item out of every workstream listing it and into another live one, `lookout remove <input>:<id>` takes an item out of every workstream listing it, so it is offered in `unplaced` as any item no workstream holds is, and `lookout rename <workstream> <new-name>` renames a workstream, live or completed. They edit the configuration file as `adopt` does, and `snapshot` counts each as a logged change rather than a hand edit. Removing the last member of a supplied input leaves it expecting records only if its `expect_records` says so. (#14)
- `lookout show` prints one setting's readout as plain text that fits 80 columns, counting each character as one column. Workstreams appear in their stated order. Each row shows the time since the workstream was last touched, `stale` once that is longer than `event_window`, or `unread` when nothing was read for it, and its members per input, with how many no input supplied. A row starting with `!` draws on an input that is degraded or in error. Below the rows, a warning names each such input with its reasons, and each workstream that draws on one. A last line counts the unplaced and dismissed items and the completed workstreams, starting with `!` while any input is degraded or in error. It is a stopgap for reading the readout, not the graphical dashboard. (#17)
- `lookout dismiss <input>:<id>` hides an unplaced item until it is touched again, and `lookout unplaced` lists unplaced items one per line, each starting with the `<input>:<id>` token `adopt` and `dismiss` take. When the id holds a tab or line break the token is printed in double quotes with the character escaped, and `adopt` and `dismiss` accept it in that form; pass it to the shell in single quotes. (#6)
- A state directory per setting, at `$XDG_STATE_HOME/lookout/<setting>/`, holding a log of every `adopt`, `move`, `remove`, `rename`, `order`, `complete` and `dismiss` run against a configuration file that exists and was selected, with whether it succeeded, was refused, or failed, so the effort of keeping the configuration current can be measured. Commands for one setting take turns on its state, so two run at once never interleave. State is kept on Unix systems only. (#6, #14, #16)
- `lookout snapshot` records one line a day in the setting's state directory, as `baseline.jsonl`: the items unplaced, and those that arrived since the last record, whether adopted, dismissed, placed in a workstream by hand, or still waiting. An item is not counted as arriving when it was already unplaced on the first day, or when its input last read healthy and it was already showing; an input with no healthy reading yet, such as one just added, has what it shows taken as already there. The record also holds the members placed by hand; how many live workstreams moved within `event_window`; the median and 85th percentile time since each live workstream was touched, counting aside those with nothing read; how many workstreams were completed since the last record; whether the workstreams changed in a way no logged command explains; whether the inputs, `discovery_window` or `forge_owners` changed; and each input's health, flagging a record taken while one was failing or degraded. Where the setting has a `github` input, the record also lists the pull requests you authored, within the github.com owners in `forge_owners`, that merged since the last record that read them, each with the time it merged and whether it targeted the branch that is its repository's default when read. A merge GitHub's search finds late is listed on the next record, so count merges by the time they merged rather than by record. A read that fails, for any one owner, is recorded as failed rather than as no merges, and said so on stderr; the next read that succeeds covers its interval, opening no more than 90 days back. The first snapshot of a local date is kept; a later one that day, or one on a date before the last record's, writes nothing. The baseline is lookout's own state, not a published contract. (#11, #12)
- Git inputs (`kind: git`), read live from `repos:`, a list of repository paths or glob patterns where `~/` is the home directory. Each local branch becomes an item with the id `owner/repo:branch`, or `host/owner/repo:branch` off github.com, with the host, owner and repository in lowercase; it is touched at its last commit and carries its repository's path and the worktrees that have it checked out. A repository's default branch and branches matching `ignore_branches` are never offered, a bare repository offers only branches a worktree has checked out, and two clones of one remote give one item. A pattern skips directories that are not repositories. Requires git 2.36 or later, and an older git is reported as such. (#7)
- `forge_owners`, required once a git, github or claude_code input is configured: only repositories whose `origin` belongs to a listed owner are read, only pull requests and issues a listed owner holds, and only Claude Code sessions whose working directory lies in such a repository, judged by the repository at that directory when lookout reads it. An entry is an owner on github.com, which must be a name GitHub allows, or `host/owner` for another host, matched without regard to case. Repositories and session working directories the fence keeps out are counted in `excluded_count` and never named, except a `repos:` entry or member echoed as the configuration writes it. (#7, #8, #9)
- `discovery_window`, defaulting to `event_window`: a git, github or claude_code input offers as unplaced only work touched within it, while an item a live workstream names is read at any age. (#7, #8, #9)
- Git input health: a missing path or a pattern matching no repository (`missing`), a path that is not a repository (`not_a_repository`), and a repository git cannot read or a directory lookout cannot look into (`git_failed`), counted rather than named when a pattern reached it, make the input `degraded` while other repositories are still read, and `error` when none could be; a commit dated ahead of the clock is `clock_skew`, and a branch lookout cannot represent, whose name is not UTF-8 or whose date git prints out of range, is left out and reported. A deleted member branch is not a failure, so a git input is `empty` only when `expect_records` says it should have branches and it has none, however old. (#7)
- GitHub inputs (`kind: github`), read live from github.com with the token `gh auth token --hostname github.com` gives, which is `GH_TOKEN` when that is set. Open pull requests you authored and open issues assigned to you are discovered for each github.com owner in `forge_owners`, and a member is read by number in any state, merged and closed included. Each becomes an item with the id `owner/repo#N` in lowercase, touched at its last update, started when it was opened, in state `open`, `draft`, `merged` or `closed`, linking its page and carrying its type, repository, number, and a pull request's branch. A github input needs a github.com owner in `forge_owners`. A member outside the fence is never requested, and a returned item owned by anyone outside it, such as a transferred repository's, is counted in `excluded_count` and never named. (#8)
- GitHub input health: no token from gh, or one github.com refuses (`auth_failed`), a rate limit (`rate_limited`), a search with more matches than GitHub returns or that stops paging early (`truncated`), and any other failed request (`github_failed`) make the input `degraded` when anything was read and `error` when nothing was; an update dated ahead of the clock is `clock_skew`. A member that is not found is shown as unread without degrading the input; one GitHub refuses to show degrades it while the other members are still read, and one whose repository has moved is shown as unread with its new id when the new owner is in `forge_owners`. (#8)
- Claude Code inputs (`kind: claude_code`), read live from the session transcripts in each of `config_dirs`, a list of Claude Code configuration directories such as `~/.claude`. Each repository and branch a session worked on becomes one item, with the same id a git branch has, or the repository's part of that id alone for a detached checkout; it is touched at the newest record any session made there and carries its repository's path, its branch, and the ids of the sessions in the transcripts lookout read, newest first, for `claude --resume`. The newest session's generated title becomes the item's title when that whole session worked on this one item, and the branch name otherwise. Subagent transcripts are skipped. A session in a worktree Claude Code has since removed is placed through the repository the worktree was made from. Branches matching `ignore_branches` are never offered. Reading needs git, which places each working directory in its repository. (#9)
- Claude Code input health: a configured directory that is missing (`missing`), a directory or transcript lookout cannot read (`unreadable`), records that no longer carry the working directory, branch and time lookout reads, or a transcript of a prompted session holding no conversation record it recognizes (`unrecognized_format`), and a repository git cannot read (`git_failed`) make the input `degraded` when anything in the discovery window was read and `error` when nothing was; git missing is `error` once there is a session to place, and a record dated ahead of the clock is `clock_skew`. With `expect_records`, the input is `empty` when the transcripts last modified within the discovery window hold no admitted session. Working directories that no longer exist or lie in no repository are counted in `details` rather than in `excluded_count`, and a member whose transcripts have aged out is shown as unread without degrading the input. (#9)
- Published contracts in `schema/`: `supplied.v1` for suppliers, `readout.v1` for renderers, and `health.v1` for input health. A health record carries `details`, one line per finding for people, and `excluded_count`; its `reasons` may gain values within version 1, so a consumer should show one it does not know. (#5, #7)
